# Handoff 2 report

Cockpit now has explicit Later and Library membership over the same ContentPiece identity. The inspection list has All, Later, and Library views with add/remove controls; an observed query supplies the rows and an `@Observable` model owns the writes. Repeat admission preserves the first admission date. Removal deletes only the membership row, retaining the ContentPiece, Artifacts, provenance, and readable substance. No automatic admission or expiry was introduced.

Normalized text has moved out of ContentPiece. The migration copies every non-null value into `LocalNormalizedText` before dropping the old column, without rebuilding ContentPieces or touching Artifact rows. The old migrations remain unchanged. S1 refused to construct a sync engine, so the dropped column never belonged to a synced schema. The migration test seeds the actual S1 schema with null, empty, Unicode, embedded-NUL, and 1.2 MB text values, runs the migration twice, and checks the retained text and evidence. This verifies a populated SQLite database, not an upgrade on Jon's iPad.

`LibraryNormalizedText` is the sync projection of that substance. Its one foreign key points to Library membership with `ON DELETE SET NULL`; its stable primary key is the ContentPiece UUID. Admission projects local text, later ingest refreshes it, and received text is retained locally. Membership removal nulls the projection's owner and text without deleting either text row. The null-owner trigger also strips stale unowned text. This is how D6's Library-only rule is expressed without a row filter that SQLiteData does not provide. Incoming sync does not promote stale local text over a server body; the documented `SyncEngine.$isSynchronizing` guard suppresses that outbound projection. A later ingest can supply a missing body for membership admitted on another device.

Memberships use their ContentPiece UUID as a primary key and a logical relationship, not a SQL foreign key. Admission requires an existing ContentPiece, and destination reads start from ContentPieces and join the memberships, so an out-of-order CloudKit membership cannot surface an unrelated row — now tested directly rather than asserted. SQLiteData 1.12.0 rejects a single foreign key with NO ACTION or RESTRICT; CASCADE is expressly prohibited for these tables, and SET NULL is incompatible with a non-null membership primary key. That trio is the whole reason, and it is sufficient on its own: an earlier draft of this report also offered out-of-order CloudKit arrival as a justification, which was wrong. SQLiteData parks a record that violates a foreign key and retries it, which is exactly why the one foreign key this slice does keep, on `LibraryNormalizedText`, is safe. The narrow application-enforced relationship preserves the contract's columns and removal behavior. This representation is called out for architectural review; it adds no alternate domain entity or deletion policy.

The other proposal for the architect is `LibraryMembership.admittedBy = "explicit"`. That is the only writer implemented. It distinguishes direct human admission without guessing the vocabulary or behavior of the future automatic Library policy. No ratified product decision was changed. The two earlier S2 criterion conflicts were already corrected by PR #5; this implementation uses those amended criteria.

CloudKit sync now starts in the live bootstrap. Exactly InterestArea, Stream, ContentPiece, LaterMembership, LibraryMembership, and LibraryNormalizedText are registered. Artifacts, raw source text, and LocalNormalizedText are absent. Existing iCloud entitlements are retained and remote-notification background mode is added. The former refusal test is replaced by a test that starts SQLiteData's mock-backed engine, sends records, inspects the resulting record types and fields, then removes Library membership and verifies that the next sent projection has no text asset.

There is no application chunk size or text threshold. The Library projection stores UTF-8 as a SQLite BLOB, which the resolved SQLiteData 1.12.0 serializer transports as a CKAsset. Apple's [CKRecord documentation](https://developer.apple.com/documentation/cloudkit/ckrecord) limits ordinary record data to 1 MB and excludes assets. The mock test sends a 1.2 MB UTF-8 body and verifies that the transport field is an asset and the database bytes are unchanged. This uses SQLiteData's existing transport rather than introducing an upload manager. It is not the deferred media/PDF/sole-source payload Asset spike, and it does not establish live CloudKit transfer reliability or arbitrary asset-size support. The test's 400,000 three-byte characters deliberately exceed the documented 1 MB record limit; it is a fixture size, not product policy.

I refused to build Edition, judgment, Personal Knowledge, PendingFind, automatic Library admission, or LocalAvailability. They have no role in this slice. PendingFind's portion of invariant 3 remains assigned to the slice that creates its table. Invariant 7 is checked only structurally here: removing an Artifact payload reference leaves normalized text intact; no actual offline-expiry behavior exists yet. Search and a Reader design pass also remain outside this minimal destination UI.

## Addendum — architect review, same day

Two defects were found in review and are fixed here. Both were our code against what a dependency actually does, rather than anything the tests could have caught unprompted.

`ON DELETE SET NULL` was carrying two meanings. This slice used it to signal "membership gone, strip the synced body," but SQLiteData issues the identical statement — deliberately marked as not synchronizing — to recover from a CloudKit `.referenceViolation`. A transient server-side reference failure therefore stripped the body of a piece that was still a Library member, and propagated the empty projection to every device, with nothing to restore it. Removal is now signalled by an `AFTER DELETE` trigger on `libraryMemberships`, and the receive triggers key their strip off whether a membership row exists rather than off the detached foreign key. Both halves are needed: the review initially proposed only the second, and the executor's test proved that insufficient, because once recovery has detached the key, deleting the membership fires no foreign-key action at all.

The sync enablement gate was decorative. `CloudSyncConfiguration` declared `enabledDefaultsKey`, `enabledEnvironmentKey` and `enabledLaunchArgument`, and nothing read any of them; the engine was constructed already started in live, against CloudSyncKit's documented contract that the app constructs it stopped and calls `startIfManuallyEnabled` from `init()`. First launch would have pushed records to the container unbidden, hardening the CloudKit schema at a moment nobody chose, and skipping the iCloud-availability check. The engine is now constructed stopped and started through the gate. **Sync is off until `-CockpitCloudKitSyncEnabled` is passed once**, which `persistManualEnablementFromLaunchEnvironment` then persists so later Home Screen launches still sync. That flag is the mechanism for step 4 of Jon's device pass.

Smaller review items: invariant 12 now has the read-surface test that actually holds it under sync, not only the application guard; `supplyLibraryTextIfMissing` documents the trigger it depends on and the test that protects it; the inert `ON CONFLICT REPLACE` clause is annotated rather than removed, since it binds to NOT NULL and editing a migration for cosmetics is a worse trade; `DestinationMigration.swift` joins the lint exclusion whose stated rationale already covered it; and a stray blank line is gone.

Verification after the fixes: 23 tests pass, `swiftlint lint --strict --no-cache` is clean over 19 files, and the unsigned generic-iOS build succeeds. Still unclaimed, unchanged from above: live CloudKit transfer, multi-device behaviour, and the migration against Jon's actual device.

One process note. These fixes were written by the reviewing architect rather than the executor, because the executor's session ended. That removes the second pass that found the defects in the first place, and the correction above — where the review's own proposed remedy was wrong — is the argument for why that pass matters.
